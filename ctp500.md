# CTP500 browser printing

Phone-accessible Chisel copy:
https://johnrigler.github.io/chisel/ctp500-test.html?v=20261016-ble3

Serve `ctp500-test.html`, `ctp500-test.js`, `ctp500.js`, and `ctp500-ble.js` together on HTTPS
or localhost. These are plain browser files for static/IPFS hosting; no
printing server, Node.js runtime, or build is required.

- Phone: disconnect Bluetooth Internals/InstaPrint, click **Connect BLE (phone)**,
  select **Teal Printer**, then **Print diagnostic receipt**.
- Chromebook/desktop: pair the printer in system Bluetooth settings, click
  **Choose Serial (Chromebook)**, then **Print diagnostic receipt**.
- Check page version `20261016-ble3`. The **Faster** preset uses paced writes
  without responses and compact raster bands. **Acknowledged** selects the
  earlier working write method. **Original pacing and raster paper feed**
  restores 20 ms pauses and white raster padding at the end.
- The diagnostic footer prints automatically after the main image.
  **Save receipt PNG** exports the live or finished receipt with its run ID.
  Photograph the entire paper receipt or share the saved PNG for diagnosis.

## Transfer timing: version 20261016-ble2

The test stream is 13,853 bytes, including 160 white raster feed rows.
Version ble1 split it into 693 awaited 20-byte writes and paused 20 ms
between writes: 692 intentional pauses, totaling 13.84 seconds before
Bluetooth/printer overhead. This is a calculation from the code, not a
measured benchmark.

Version ble2 keeps the tested 20-byte packet size and write ordering, but
removes the extra timer for acknowledged writes. Unacknowledged writes
retain 20 ms pacing. **Slower BLE transfer** restores the previous pacing
for acknowledged writes too. The status now reports elapsed send time and
bytes per second; that measures browser transfer, not mechanical print time.
John subsequently confirmed ble2 printed and supplied a screenshot showing
13,853 bytes in 68.3 seconds (203 bytes/second), with the slower-transfer
checkbox unchecked. That screenshot is the measured baseline for ble3.
Failed chunks are never retried automatically.

`feedRows: 160` adds white raster rows to move the image to the tear edge.
A failed partial raster can leave the printer expecting image bytes;
restart it before a fresh attempt. Bluetooth Internals hex input requires
`0x`; the module sends Uint8Array bytes directly, not hexadecimal strings.

## Diagnostic receipt and optimization: version 20261016-ble3

The measured ble2 baseline averages approximately 98.6 ms per 20-byte write
(68.3 seconds / 693 writes). It does not reveal the exact radio connection
interval. The blank raster feed accounts for 7,680 of its 13,853 bytes.

The faster preset uses the already advertised Write Without Response method,
still awaiting every browser call and still limiting packets to 20 bytes.
A minimum 25 ms start interval (at most 800 bytes/second before overhead)
limits the rate across both receipt sections; it adds only the remaining
interval after a quick call, not an extra pause after an already slow call.
Larger ATT payloads and parallel GATT writes are not assumed or probed.

`ctp500EncodeBands` emits standard eight-row GS v 0 images with unused right
columns omitted independently for each band. White bands retain their height,
so the output positions match the full raster. It sends the normal setup only
once; the footer continues the existing stream without resetting the printer.
The existing encoder's defaults remain byte-for-byte compatible with ble2.
Other presets retain full-width rasters for comparison.

The main image has no trailing white padding. The normal final footer uses
eight LF bytes for paper feed instead of 160 full raster rows. LF commands
physically advanced paper in the earlier manual phone test; the exact feed
distance depends on firmware line spacing. The Original preset retains the
old white raster padding if the compact feed is unsuitable on another unit.

While the main image sends, the page records accepted bytes, write count,
write-call latency, elapsed time at 25/50/75/100 percent, actual pause time,
and page-hidden duration. Its raster footer prints these measurements,
together with actual write method, packet size, pacing, browser version,
device name, timestamp, and run ID. The statistics explicitly cover the main
image only: its measurements exist before the footer can be rendered.
Footer duration and overall browser-send time appear separately on screen.
A completed browser write is not a printer status/ink confirmation.

The preview updates during transmission. Save receipt PNG captures that live
or finished canvas; a completed receipt PNG contains the same main image and
diagnostic footer pixels submitted to the printer. Error images are labeled
NOT PRINTED. After an interrupted main raster no error footer is sent; after
a footer failure there is no automatic retry. Restart the printer first.

Validation: encoder default-byte equivalence; decoding the optimized multi-
frame stream reconstructs the same thresholded pixels as the receipt PNG;
packet order and 20-byte maximum; minimum-interval pacing and slow-call case;
acknowledged/no-response/original presets; capability fallback; failure in
either stage; PNG download path; and the retained two-stage Web Serial path.
These checks use native canvas rendering and a simulated radio. The faster
profile, compact paper feed after the new footer, and actual hardware speed
still need the next phone print. No simulated timings are hardware benchmarks.
